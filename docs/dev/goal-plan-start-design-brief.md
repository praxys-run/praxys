# Goal → plan-start brief

- **Job and audience:** A self-coached runner chooses what an accepted plan is for, with the current Goal preselected when it matches. This is an Operate flow for deciding whether to adopt a proposal, not a promise of a result. An unsupported current Goal remains unchanged while an accepted separate purpose may still be available.
- **Sequence:** The backend resolves the current Goal against the versioned capability registry and returns every accepted purpose mode. Goal shows either the matching default or that another accepted purpose is available. Training requires an explicit purpose selection before constraints, then shows the scoped baseline, transparent readiness result, proposal provenance, exact-version regeneration/rejection/adoption, and the existing delivery-consent surface only after adoption.
- **Direction:** Preserve the Field Lab's flat, warm-paper instrument layout: green for the one action at each step; cobalt for policy, version, uncertainty, and sources. Use the existing cards, alerts, sheets, inputs, and workout structure editor rather than a new navigation lane.
- **Boundaries:** Capability discovery exposes accepted policies only, resolves the owner-scoped Goal on the backend, and returns a versioned purpose contract, constraint schema, and action paths shared by web, miniapp, plugin, and MCP clients. Linked purposes carry an exact Goal ID/revision; independent purposes never mutate the Goal page. The first capability remains the accepted adult recreational outdoor-road 5K policy. Broader road and trail policies do not appear until their own science decisions are accepted. V1 accepts one shared session-duration limit, so distinct per-day limits and terrain/equipment customization remain explicitly unsupported rather than approximated.
- **States:** Loading, slow/offline and retry; no accepted policy; separate purpose available; client/policy schema mismatch; Goal revision conflict; active-plan reassessment required; legacy provenance unknown; every baseline/readiness code; missing or sparse history; contradictory availability; no-power outcome; fallback explanation; validation; draft for another purpose; draft/expired/rejected/superseded/stale/adopted lifecycle; delivery disabled, preview, failure, and conflict.
