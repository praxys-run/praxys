# Goal → plan-start brief

- **Job and audience:** A self-coached runner moves from an existing goal into the accepted plan-generation capability that matches it; this is an Operate flow for deciding whether to adopt a proposal, not a promise of a result. Goals without an accepted policy keep manual plan management and an explicit unavailable state.
- **Sequence:** The backend resolves the current goal against the versioned capability registry. Goal shows whether an accepted policy is available. Training holds the selected policy's scoped inputs, transparent readiness result, proposal clearly marked as not yet canonical, exact-version regeneration/rejection/adoption, then the existing delivery-consent surface only after adoption.
- **Direction:** Preserve the Field Lab's flat, warm-paper instrument layout: green for the one action at each step; cobalt for policy, version, uncertainty, and sources. Use the existing cards, alerts, sheets, inputs, and workout structure editor rather than a new navigation lane.
- **Boundaries:** Capability discovery exposes accepted policies only, resolves the owner-scoped goal on the backend, and returns a versioned constraint schema plus action paths shared by web, miniapp, plugin, and MCP clients. The first capability remains the accepted adult recreational outdoor-road 5K policy. Broader road and trail policies do not appear until their own science decisions are accepted. V1 accepts one shared session-duration limit, so distinct per-day limits and terrain/equipment customization remain explicitly unsupported rather than approximated.
- **States:** Loading, slow/offline and retry; no accepted policy; client/policy schema mismatch; goal/capability refresh conflict; every baseline/readiness code; missing or sparse history; contradictory availability; no-power outcome; fallback explanation; validation; draft/expired/rejected/superseded/stale/adopted lifecycle; delivery disabled, preview, failure, and conflict.
